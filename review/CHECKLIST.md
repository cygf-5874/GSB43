# 审查核对表 · blobcache

> 本表只规定**交付格式与自检项**，不给出缺陷数量、位置或现象。
> 结论一律写进 `review/REVIEW.md`，本表**勿改**。

## 一、交付物

- 唯一交付物：`review/REVIEW.md`（本目录下）。
- 不改 `src/`、`test/`、`scripts/`、`check/` 下任何文件；不新增、不提交测试代码。
  临时验证程序可以写，但**不要提交**（跑完删掉，别留在仓库里）。
- 提交前用 `git diff --stat` 自检：必须为空（`git status` 里除了 `review/REVIEW.md`
  不应有其它改动）。

## 二、保证判定表（必须逐条给判定）

`review/REVIEW.md` 的「保证判定」表必须把 README「对外保证」的 **6 条逐条列出**，
每条给出「违反」或「未违反」二者之一的明确判定，不许留空、不许写「不确定」。

- 判为**违反**的保证：必须在第三节的缺陷清单里有相应条目（保证编号一致）；
- 判为**未违反**的保证：缺陷清单里不得出现该编号的条目。

## 三、缺陷清单（六列，一行一条）

每发现一处**违反 README「对外保证」**的缺陷，就必须按下面六列写清楚，缺一列算不合格：

| 列 | 含义 | 要求 |
| --- | --- | --- |
| 保证编号 | 被违反的是 README 里第几条对外保证 | 写编号（1~6） |
| 缺陷位置 | 出错的具体代码位置 | 写成 `类文件名:成员名`（如 `SomeClass.java:someMethod`） |
| 触发输入 | 能稳定复现的最小输入 | 给出**字面量**（key、payload、字节序列、调用顺序），可直接照抄运行 |
| 可观察证据 | 跑出来的具体现象 | 期望什么 / 实际什么，**可判定**（异常类型、错误码、返回值） |
| 违反哪一条 | 一句话说明它为什么违反该条保证 | 与「保证编号」呼应 |
| 正确做法 | 应当如何修正 | 一句话，指向正确的校验 / 编码方式 |

## 四、为什么既有用例没抓到

`review/REVIEW.md` 必须单独一节说明：`test/blobcache/BlobCodecTest.java` 里**为什么没抓到**
这些缺陷（逐条说明它落在既有用例覆盖范围的哪条盲区）。

## 五、自检项

- [ ] 每条结论都能对应到 README 里**某一编号**的对外保证。
- [ ] 每条结论都给出了**可照抄复现**的具体输入与**具体现象**（期望 vs 实际）。
- [ ] 没有「可能有风险」「建议关注」「看起来不太对」「或许」这类**无法核对**的话。
- [ ] 六列表格之外，不夹带其他无关内容。

## 六、判定说明

- `bash scripts/check.sh` 是固定验收入口，只校验交付格式、可判定性与
  「保证判定 ↔ 缺陷清单」的自洽；结论**是否正确**由人按 README 保证逐条复核。
- 复现一律用 JDK 自带工具（`javac` / `java`）加载本仓库代码；
  不要引入第三方依赖，也不要把临时程序提交进来。
